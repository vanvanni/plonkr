A small setup profile

Automatic accounts, an explicitly created account, and a repository checkout.

This profile validates with the current beta. Replace the placeholder repository, key path and host before running it against a real machine. The repository's examples folder has more profiles that are tested over real SSH.

The profile

name = "Prepare application machine"

configuration {
  groups = [
    { name = "app" },
    { name = "reports", create = false },
  ]
  users = [
    { name = "app", service = true, groups = ["app"] },
    { name = "reporter", groups = ["reports"], create = false },
  ]
}

repository "your-repo" {
  url  = "git@example.com:team/your-repo.git"
  path = "/srv/your-repo"
  user = "app"
  key  = "/home/operator/.ssh/your-repo"
  ref  = "main"
}

tasks {
  task "Create reports account" {
    order = 10
    setup = [group("reports"), user("reporter")]
  }

  task "Clone application" {
    order  = 20
    setup  = [repo("your-repo")]
    script = ["echo application-checkout-ready"]
  }
}
plonk validate ./app.hcl
plonk run my-host ./app.hcl --dry-run
plonk run my-host ./app.hcl

How to read it

  • The app group and user are created automatically by the Configuration task, because they do not set create = false. app is a service account, so it gets /var/lib/app and no login shell.
  • The reports group and reporter user are created explicitly in the first task, groups before users as listed.
  • The second task copies the deploy key from the controller and clones the repository as app.
  • The shell message runs only after that task's setup phase succeeds.

The profile does not install Git, grant access at the repository provider or make /srv writable for app. Git must be on the target and the provider must accept the key; Plonkr creates a missing checkout directory for app when the SSH login is root or has passwordless sudo.

Validated inputs

The arguments reference shows profile questions, defaults and validation rules, with explicit forwarding to reusable snippets. Try the complete examples/arguments.hcl profile from the repository:

plonk validate ./examples/arguments.hcl --arg app_name=api --arg port=9000
plonk run my-host ./examples/arguments.hcl --arg app_name=api --dry-run

Omit --arg in a terminal to answer the questions before execution. Unattended runs use defaults or fail for missing required inputs. A missing snippet input is an error before any question or SSH connection.

Reusable shell work

Named snippets are called with run() in the script phase. Put definitions in snippets/*.hcl under the profiles root:

snippet "inspect-machine" {
  commands = ["uname -a", "id"]
}

# In a task:
# script = [run("inspect-machine")]

Snippet names are independent of filenames, nested calls expand in place, and cycles fail during loading. Forward declared snippet inputs explicitly with run("name", {input = args.value}); snippets never prompt or inherit the caller's inputs implicitly.

Going further

Add a lock to skip a task once it has taken effect, wait for a rebooted machine or a service to come up, and gate optional steps with flag(). See configuration and tasks, repository SSH keys and execution and results for the surrounding behavior.
