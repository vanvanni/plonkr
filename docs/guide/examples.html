A small setup profile

Automatic accounts, an explicitly created account, and a repository checkout.

Design example: this uses the proposed HCL configuration and task structure. It is not runnable with the current prototype. Exact grammar, baseline ordering and task failure rules remain under discussion.

Proposed profile

name = "Prepare application machine"

configuration {
  groups = [
    { name = "app" },
    { name = "reports", create = false },
  ]
  users = [
    { name = "app", service = true, groups = ["app"] },
    { name = "reporter", service = false, groups = ["reports"], create = false },
  ]
}

repository "your-repo" {
  url  = "git@example.com:team/your-repo.git"
  path = "/srv/your-repo"
  user = "app"
  key  = "/home/operator/.ssh/your-repo"
  ref  = "main"
}

tasks {
  task "Create reports account" {
    order = 10
    setup = [group("reports"), user("reporter")]
  }

  task "Clone application" {
    order = 20
    setup = [repo("your-repo")]
    script = ["echo application-checkout-ready"]
  }
}

How to read it

  1. The app group and user opt into automatic creation by omitting create = false.
  2. The reports group and reporter user are created explicitly in the first task.
  3. The second task requests repository setup as app, using the exact key file from the controller.
  4. In the proposed phase model, the shell message runs only after that task's setup phase succeeds.

The example assumes the proposed groups-before-users baseline and tasks in ascending order. Those ordering details still need approval. It does not install Git, grant access at the repository provider, set repository host trust, or make /srv writable for app. Those prerequisites must be prepared for an actual acceptance run.

Reusable shell work

The prototype supports named snippets referenced through run(). Keeping that capability in the script phase is proposed:

snippet "inspect-machine" {
  commands = ["uname -a", "id"]
}

# Proposed task script attribute:
# script = [run("inspect-machine")]

In the prototype, snippet names are independent of filenames, nested includes expand in place, and cycles fail during loading. Placement and discovery in the new profile directory still need to be finalized.

Before turning this into a runnable profile

Use the final schema and supported paths once released, replace the placeholder repository, supply an authorized deploy key, and prepare the target permissions and host trust. Installation and runnable command examples will be added after those paths are implemented and verified.

See configuration and tasks, repository SSH keys and execution limits for the surrounding behavior.
