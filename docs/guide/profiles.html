Profiles and locations

Keep setup instructions on the machine where you run plonk.

A profile describes setup for a target. A snippet is reusable work included by a profile. A template supplies the content of a managed file such as a service unit. These concepts exist in the prototype; their final directory layout is still being defined.

Windows profile location

Agreed location: %ProgramData%\plonkr\. Resolve %ProgramData% on the controller rather than hard-coding a drive letter. This is machine-wide storage, not a separate directory for each Windows user.

The location has been selected for the new implementation; the prototype still uses its old Documents directory. Subdirectories for profiles, snippets and templates have not been finalized. Directory creation and editing permissions still need to be specified.

Linux profile location

Proposed: /etc/plonkr/. Moving away from Documents is agreed; this exact Linux path and the layout beneath it remain proposals. A machine-wide location makes profiles easy to find, while editing may require elevated permissions.

Moving existing profiles

The new release will replace the prototype's Documents-based discovery. The migration procedure, explicit-directory override and lookup precedence remain to be defined. No automatic migration is implemented or promised yet.

Existing prototype profiles use a different schema from the proposed v2026.11.0 examples. Moving a file alone will not make it compatible. Keep the original profile while adapting it to the final format.

Loading a profile also loads its required includes, snippets and templates before execution. A bare name uses the selected profiles directory; an explicit path loads that file. Without --profiles-dir, a bare web.hcl first checks the current directory. Use a bare web name or an explicit directory override to avoid that ambiguity. Unrelated profiles are not executed.

Local paths and target paths

A repository key source is a path on the controller. The repository checkout path and the installed key path are on the target. A Windows controller may therefore reference a Windows key file while preparing a Linux target.

Private key material belongs in the source key file, not inside a profile. Native Windows source-path handling must be verified before the Windows workflow is documented as supported.
