Profile reference

Every key a profile accepts, what it does, and its default.

Profiles are HCL files ending in .hcl. This page describes the parser in the current beta. Values must be literals of the stated type: Plonkr does not convert between strings, numbers and bools, and unknown keys are rejected.

name    = "Prepare application machine"
include = ["base"]

configuration { ... }      # at most one
repository "your-repo" { ... } # any number
unit "example.service" { ... } # any number
tasks { ... }              # at most one

Top-level keys

KeyTypeWhat it does
namestringDisplay name shown in previews and logs. Defaults to the filename without .hcl. Must not be blank when set.
includelist of stringsOther profiles (by name, from the same profiles directory) to load into this one. See includes.
configurationblockUsers, groups and timezone for the target. See configuration.
repository "LABEL"blockA Git checkout on the target. See repository.
unit "NAME"blockA systemd unit rendered from a template. See unit.
tasksblockThe ordered work to run. See tasks.

A profile must expand to between 1 and 10,000 steps. The legacy prototype blocks script, scripts and account are rejected with an error.

configuration

Declares the accounts and timezone the machine should have. Groups and users with create = true (the default) and the timezone become an automatic first task called Configuration, which runs before your own tasks in this order: groups, users, timezone.

KeyTypeWhat it does
groupslist of objectsLinux groups. Fields below.
userslist of objectsLinux user accounts. Fields below.
timezonestringIANA timezone such as "Europe/Amsterdam" or "UTC", applied to the target. At most 128 characters.

Group fields

FieldTypeDefaultWhat it does
namestringrequiredGroup name: lowercase letters, digits, _ and -, starting with a letter or _, at most 32 characters. root is not allowed.
gidintegersystem picksFixed numeric group ID, from 1 to 4294967294. Must be unique within the profile.
createbooltrueCreate the group in the Configuration task. With false, it is only created where a task calls group("NAME").

User fields

FieldTypeDefaultWhat it does
namestringrequiredUser name, same rules as group names. root is not allowed.
serviceboolfalseMarks a service account. Changes the defaults for home and shell.
homestring/home/NAME, or /var/lib/NAME for a service accountHome directory. Must be a clean absolute path.
shellstring/bin/bash, or /usr/sbin/nologin for a service accountLogin shell. Must be a clean absolute path.
groupslist of stringsnoneSupplementary groups. A user created automatically cannot list a group declared with create = false, because that group may not exist yet.
public_keyslist of stringsnoneSSH public keys allowed to log in as this user, one authorized_keys line each, without options.
createbooltrueCreate the user in the Configuration task. With false, it is only created where a task calls user("NAME").
configuration {
  groups = [
    { name = "app", gid = 1001 },
    { name = "reports", create = false },
  ]
  users = [
    { name = "app", service = true, groups = ["app"] },
    { name = "reporter", groups = ["reports"], create = false },
  ]
  timezone = "Europe/Amsterdam"
}

repository

Declares a Git checkout on the target. The label names the repository: letters, digits, ., _ and -, starting with a letter or digit. A task clones it with repo("LABEL").

KeyTypeDefaultWhat it does
urlstringrequiredClone URL: ssh://, https:// or git@host:path. Must not contain a password, query or fragment.
pathstringrequiredAbsolute checkout path on the target.
userstringrequiredTarget user that owns the checkout and runs Git.
keystringrequired for SSH URLsAbsolute path to the deploy key on the machine running plonk (a Windows path like C:/Users/you/.ssh/key is accepted). The file is copied unchanged to ~/.ssh/plonkr-LABEL.key for user. Not allowed with https:// URLs, which never use it: a repository with an https:// URL and a key is rejected when the profile is loaded.
refstringremote default branchBranch, tag or full commit hash to check out. Do not prefix it with refs/.
known_hostslist of stringsnoneknown_hosts lines appended to the target user's ~/.ssh/known_hosts. Plonkr's own clone accepts the server's host key automatically either way; see repository SSH keys.
repository "your-repo" {
  url  = "git@example.com:team/your-repo.git"
  path = "/srv/your-repo"
  user = "app"
  key  = "/home/operator/.ssh/your-repo"
  ref  = "main"
}

unit

Declares a systemd unit file. The label is the unit's filename and must end in a systemd suffix such as .service, .timer or .socket. A task installs it to /etc/systemd/system/ with unit("NAME").

KeyTypeDefaultWhat it does
sourcestringrequiredTemplate path relative to the files/ directory next to your profiles. It cannot leave that directory. UTF-8, at most 1 MiB.
varsobject of stringsnoneValues substituted into the template as ${name}, using HCL template syntax.
unit "example.service" {
  source = "example.service.tmpl"
  vars = {
    user       = "app"
    exec_start = "/usr/local/bin/example-server"
  }
}

tasks

Holds named task blocks. Tasks run in ascending order, after the Configuration task. Within a task, all setup steps run before all script steps, regardless of where the keys appear.

KeyTypeDefaultWhat it does
orderintegerrequiredPosition of the task, 0 or higher. Must be unique within the profile.
bypassboolfalseSkip this task and report it as bypassed. plonk run --bypass "NAME" does the same for a single run.
lockblocknoneBypass this task when the target already matches. See lock.
setuplistnoneManaged operations on declared resources. See functions.
scriptlistnoneShell commands as strings, plus run(), flag() and log(). Each string runs in its own remote shell, so a cd does not carry over.

Each task needs at least one step in setup or script.

lock

An optional block inside a task. When it holds, the whole task is bypassed and the run moves on to the next task. Both keys are optional, but at least one is required, and they can be combined. The task is bypassed only when every directive you set holds; if any one does not, the task runs.

KeyTypeHolds when
existslist of absolute pathsEvery path exists on the target. Nothing is stored.
evallist of commandsEach command is run on the target over SSH as the login user, and the results (exit status and standard output) equal those recorded after the task last completed. With no record, the task runs.
task "Install Go" {
  order  = 10
  script = ["./install-go.sh"]

  lock {
    exists = ["/usr/local/go/bin/go"]
    eval   = ["/usr/local/go/bin/go version"]
  }
}
  • When state is recorded. After the task completes, its eval commands run again and the results are saved. A failed task saves nothing. A failing eval command is not an error: its exit status is part of the result.
  • Where. On the target, in /etc/plonkr/.states/, one private file per profile, written as root or through passwordless sudo. A rebuilt machine has no state, so its tasks run. A lock with only exists needs no state and no privileges.
  • Edits. Changing a lock block discards the saved result for that task, so it runs once more.
  • Reporting. A lock-bypassed task is reported as bypassed, with the reason bypassed by lock. Bypass flags and --bypass take precedence, so a bypassed task never evaluates its lock.
  • Overriding. plonk run --force runs locked tasks anyway and refreshes their saved results. --dry-run does not connect, so it cannot evaluate locks; it notes that they are checked when the task runs.
  • Limits. Locked tasks must have unique names, because the name keys the saved state. eval commands run on every run, so keep them read-only and free of secrets; their output is not logged, but the commands are part of the profile. Running two plonk run commands against the same target and profile at once is not supported.

Beta: locks have been exercised over real SSH on Ubuntu 24.04 with a non-root login using sudo. Other distributions and native Windows controllers are unverified.

Functions

FunctionWhereWhat it does
group("NAME")setupCreate a group declared in configuration.
user("NAME")setupCreate a user declared in configuration.
repo("LABEL")setupInstall the deploy key and clone a declared repository. An existing matching checkout is verified, not updated.
unit("NAME")setupInstall a declared unit file.
run("SNIPPET", ...)scriptInsert the commands of one or more snippets.
flag("NAME", STEP, ...)setup, scriptRun the steps only when --NAME is passed to plonk run; otherwise they are reported as skipped. Names are lowercase with -. Names of built-in options are reserved and rejected when the profile is loaded: help, tty, dry-run, no-tui, profiles-dir, bypass, version, auto-approve and force.
log("MESSAGE", "COLOR")setup, scriptPrint a message locally. The optional color is one of default, black, red, green, yellow, blue, magenta, cyan, white or gray.
tasks {
  task "Deploy application" {
    order  = 20
    setup  = [repo("your-repo"), unit("example.service")]
    script = [
      run("inspect-machine"),
      flag("vm", "echo running-in-a-vm"),
      log("Application setup complete", "green"),
    ]
  }
}

Snippets

Snippets are reusable script steps. Put them in .hcl files in a snippets/ directory next to your profiles; filenames do not matter, snippet names must be unique. A snippet's commands list accepts the same items as script, including nested run() calls. Cycles are rejected, and nesting is limited to 64 levels.

snippet "inspect-machine" {
  commands = [
    "uname -a",
    flag("verbose", "id"),
  ]
}

Includes

include loads other profiles into this one. Their Configuration tasks run first, then this profile's Configuration task, then the included tasks, then this profile's own tasks. Resources from an included profile stay private to it: refer to them from that profile's own tasks, not from the including profile. Include cycles are rejected.

A profile is merged once, however many include paths reach it. If left and right both include base, base runs once, at the position where it is first reached (depth first, in the order listed). Listing the same profile twice in one include list is an error, because it is almost always a typo. A locked task in a shared profile is therefore valid.
