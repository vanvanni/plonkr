Execution and results

Understand what will run and what actually happened.

Plonkr expands profiles and snippets before executing a sequential plan over SSH. It checks argument contracts, collects all profile answers, then validates the fully resolved plan, including resources, locks and rendered templates, before it reads deploy keys, opens a run log or connects. Supply repeatable --arg name=value options for unattended runs.

Preview before applying

plonk validate PROFILE checks a profile fully offline and prints the expanded plan. It never prompts; with required inputs missing it checks argument contracts and lists what is missing.

plonk run HOST PROFILE --dry-run resolves inputs like a real run and renders unit templates, then shows planned, skipped and bypassed work without SSH or reading repository key files. Task locks are not evaluated, because that needs the target. A plugin step may read its external API to show differences, but never changes anything. A preview is a plan, not evidence that credentials, privileges or remote dependencies will work.

Result meanings

Every step and task ends in one of these states, on screen and in the run log:

  • Completed: the step ran and succeeded.
  • Failed: the step returned an error. The run stops here.
  • Skipped: the step is gated by a flag() that was not passed.
  • Bypassed: the task was bypassed by bypass = true, --bypass or a holding lock. Its steps do not run, and the run continues.
  • Planned: shown by a dry run for work that would run.
  • Cancelled: the run was interrupted, for example with Ctrl+C.
  • Pending: work never reached because an earlier step failed or the run was cancelled.

Bypass is not “ignore errors and continue”: a bypassed task simply does not run.

Failure and repeat runs

Work stops at the first failure. There are no automatic retries, rollback or resume, so a failed step may leave partial changes on the target. Fix the cause and run the profile again: managed operations accept work that is already done, such as an existing group or a matching repository checkout, which is verified rather than updated. Use locks to bypass your own tasks once they have taken effect.

Each shell item uses a separate remote shell: a cd or variable assignment in one item does not carry into the next. Keep dependent shell operations together. Cancellation stops local SSH but cannot guarantee that every remote descendant stops.

Output and logs

In a terminal, plonk run shows a live screen. --no-tui, piped output, --tty and runs that may ask for approval (deploy-key replacement or plugins) use plain output, with [completed], [failed], [skipped], [bypassed], [planned] or [cancelled] on each step.

Each run that reaches execution saves a private log of commands, output and results. It lives in $XDG_STATE_HOME/plonkr/logs (or ~/.local/state/plonkr/logs) on Linux and in the user cache under plonkr\logs on Windows; set PLONK_LOG_DIR to an absolute path to change it. Terminal control sequences are stripped from output and logs, and inline sensitive plugin attributes are redacted, but ordinary commands and output are logged as they are: do not print secrets.

Exit codes

  • 0: success.
  • The failing remote command's own status when a step fails, or 255 when SSH cannot connect.
  • 130: cancelled.
  • 1: any validation, argument or local error. These happen before any SSH connection.

Platforms and privileges

Managed operations assume Linux tools; unit installation needs systemd. Account, timezone, unit and lock-state changes need root or passwordless sudo for the SSH login. Profiles execute trusted shell code with those privileges.

Real SSH acceptance runs on Ubuntu 24.04. Other distributions are likely to work where the same tools exist, but are not verified. The Windows controller builds and passes its native tests; its OpenSSH transport has not yet been verified end to end.
