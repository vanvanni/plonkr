Configuration and tasks

Describe the machine's accounts separately from its ordered setup work.

A profile has a configuration block for accounts and the timezone, and a tasks block for ordered work. Every key is listed in the profile reference.

Automatic and explicit creation

Users and groups declared in configuration are created automatically unless they set create = false. The same rule applies to both. Automatic resources and the timezone form a first task called Configuration, which runs groups, then users, then the timezone, before your own tasks.

create = false means “do not create automatically”. A task can still create that resource at a chosen point with group("NAME") or user("NAME"). A user created automatically cannot list a group declared with create = false in its groups, because that group may not exist yet.

Runs can be repeated. An existing group is accepted, as long as its GID matches a declared gid. An existing user is accepted when its home directory and shell match the declared values; otherwise the step fails rather than changing the account. Supplementary groups and public keys are added on every run. Plonkr never modifies a UID 0 account.

Users and groups

A user has a name and optional service, home, shell, groups and public_keys. A service account defaults to /var/lib/NAME and /usr/sbin/nologin and is created as a system account; other users default to /home/NAME and /bin/bash. A group has a name and an optional fixed gid.

configuration {
  groups = [
    { name = "app" },
    { name = "reports", create = false },
  ]
  users = [
    { name = "app", service = true, groups = ["app"] },
    { name = "reporter", groups = ["reports"], create = false },
  ]
  timezone = "UTC"
}

Here app is created automatically by the Configuration task. The reports group and reporter user wait for an explicit setup operation. Public keys grant login access to the target; repository deploy keys serve a different purpose.

Named tasks and phases

Tasks are named and carry a unique numeric order. A task can contain managed setup operations, script shell commands, or both. Within a task, all setup steps run before all script steps, wherever the keys appear.

tasks {
  task "Prepare reports account" {
    order  = 10
    setup  = [group("reports"), user("reporter")]
    script = ["echo reports-account-ready"]
  }
}

The phase boundary is enforced when the profile loads: group(), user(), repo() and unit() belong in setup, and shell strings and run() snippet calls belong in script. flag(), log() and the waiting functions work in both. Each shell string runs in its own remote shell, so a cd does not carry over to the next one.

A task can also be skipped: set bypass = true, pass --bypass "NAME" for one run, or add a lock so it is bypassed once the target already matches.

Ordering

A run executes in this order:

  1. The Configuration tasks of included profiles, then this profile's own Configuration task.
  2. Tasks of included profiles, in their own order.
  3. This profile's tasks, in ascending order.

Within a task, setup comes before script. Work runs one step at a time and stops at the first failure, so a script never runs after its task's setup failed. See execution and results for what happens next, and includes for how shared profiles merge.
