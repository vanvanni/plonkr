Repository SSH keys

Use the key file you already have to give the target access to a repository.

Agreed for v2026.11.0: the repository refers to a key file on the machine running plonk. Plonkr copies that file byte-for-byte to the selected target user's .ssh/. It preserves the local source and does not generate a key, decrypt it or re-encode it.

Destination and identity

The key is installed directly as ~/.ssh/plonkr-REPOSITORY.key for the selected target user, without an application subdirectory. Identical bytes require no approval. A different existing key triggers a warning and a default-no confirmation. Use --auto-approve to approve replacements without prompting; the warning is still printed. Declining or providing no answer preserves the existing key.

The private-key store and stored-key identifiers have been removed. Specify a local file path instead of importing a key into Plonkr.

Repository declaration

repository "your-repo" {
  url  = "git@example.com:team/your-repo.git"
  path = "/srv/your-repo"
  user = "app"
  key  = "/home/operator/.ssh/your-repo"
  ref  = "main"
}

Proposed HCL example: key is local to the controller; path and user describe the target. The example hostname is a placeholder. A proposed setup operation repo("your-repo") would perform repository setup.

For a Windows controller, a candidate HCL source path is key = "C:/Users/operator/.ssh/your-repo". This is a design example; native Windows path support is not verified.

What a successful clone requires

  • The repository provider must authorize the matching public key.
  • The target user must exist and have permission to create the checkout.
  • Git and OpenSSH must be available on the target.
  • Repository SSH server keys are accepted automatically, including unknown or changed keys.
  • An encrypted private key must be usable by SSH when Git authenticates.

Connecting from your controller to the target and connecting from the target to the repository are separate SSH connections. Copying a repository key does not grant repository permissions. Repository Git operations use automatic host-key acceptance and do not verify server identity against known_hosts. The controller-to-target connection continues to use your OpenSSH host-key policy.

Encrypted files

An encrypted key remains encrypted after copying. Removing the store does not remove the need to unlock that key for authentication. The current beta rejects encrypted source keys during local preflight. Use an unencrypted deploy-key file; its bytes are copied unchanged.

What the prototype establishes

The prototype has a direct-file transfer path with SHA-256 verification, private file permissions and strict repository host-key checking. It also has a legacy store path that transforms the file. The new contract keeps unchanged copying and removes the store and application key subdirectory.

The beta verifies a matching existing checkout without updating it. Target key replacement requires the approval described above. Repository authorization, missing software and filesystem permissions can still cause an operation to fail.
