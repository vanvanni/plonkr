Repository SSH keys

Use the key file you already have to give the target access to a repository.

A repository refers to a deploy-key file on the machine running plonk. Plonkr copies that file byte-for-byte to the selected target user's ~/.ssh/. It preserves the local source and does not generate, decrypt or re-encode the key.

Destination and identity

The key is installed directly as ~/.ssh/plonkr-REPOSITORY.key (mode 0600) for the selected target user, without an application subdirectory. Identical bytes require no approval. A different existing key triggers a warning and a default-no confirmation. Use --auto-approve to approve replacements without prompting; the warning is still printed. Declining, or running unattended without --auto-approve, preserves the existing key.

Each keyed repository gets a managed SSH alias, such as your-repo.github.com, in the target user's ~/.ssh/config. The alias selects the deploy key, and Git uses it for the clone and for later pulls, so several repositories on one host can each use their own key. Explicit SSH URL ports are kept. Repeated runs update the managed block without duplicating it, and unrelated SSH settings are preserved.

Host your-repo.github.com
  HostName github.com
  IdentityFile ~/.ssh/plonkr-your-repo.key
  IdentitiesOnly yes

Repository declaration

repository "your-repo" {
  url  = "git@example.com:team/your-repo.git"
  path = "/srv/your-repo"
  user = "app"
  key  = "/home/operator/.ssh/your-repo"
  ref  = "main"
}

key is a path on the controller; path and user describe the target. The hostname is a placeholder. A task clones the repository with setup = [repo("your-repo")]. On a Windows controller, write the key path as key = "C:/Users/operator/.ssh/your-repo". key is only for SSH URLs: an https:// repository with a key is rejected. All fields are listed in the profile reference.

What a successful clone requires

  • The repository provider must authorize the matching public key.
  • The target user must exist. When the checkout path does not exist and the user cannot create it, Plonkr creates it for that user if the SSH login is root or has passwordless sudo.
  • Git and OpenSSH must be available on the target.
  • The key must be unencrypted, use LF line endings and end with a newline. These are checked locally before connecting.

Connecting from your controller to the target and from the target to the repository are separate SSH connections. Copying a repository key does not grant repository permissions. Repository Git connections accept unknown or changed server host keys automatically and do not verify them against known_hosts, including later pulls through the checkout's saved SSH command. The controller-to-target connection keeps your normal OpenSSH host-key policy.

Encrypted files

The beta rejects encrypted source keys during local preflight, before any connection. Use an unencrypted deploy-key file; its bytes are copied unchanged.

Repeat runs

An existing checkout of the same repository is verified, not updated: Plonkr does not pull for you. Existing checkouts are moved to the managed SSH alias. An empty existing directory is accepted as a clone target; a non-empty directory that is not the expected repository is refused. Repository authorization, missing software and filesystem permissions can still make the step fail.
